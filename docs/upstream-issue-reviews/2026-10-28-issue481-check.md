# Issue #481：GPT 和 Gemini 账号令牌过期

## 结论

Issue #481 的失效路径已在隔离环境复现：账号记录中存在 `refreshToken`，但 access token 过期或第一次模型请求返回 401 时，Codex/Gemini 路径没有把刷新令牌交给刷新端点，而是直接把账号标成无效，要求用户重新登录。

本分支修复了两类内置插件：

```text
Cursor 模型请求
  → PluginRegistry::stream_model
  → ResourceDefinition.prepare（按账号串行）
  → 保存 access/refresh token 轮换结果
  → Provider.invoke
  → 401 时返回 auth-error
  → 宿主只重试一次，且重试前已持久化新凭证
```

实现依赖 PR #4 引入的插件 API 2 `prepare` 生命周期；本分支基于该分支叠加，PR #4 仍需真实 Grok 账号验收，因此本 Issue 的修复也不能单独从当前主线构建合入。

## 隔离复现

复现脚本使用假 JWT、假 refresh token 和合成 HTTP 响应，不读取或发送正式账号凭据：

| 插件 | 原行为 | 结果 |
| --- | --- | --- |
| Codex / GPT | `refreshToken` 已存在，usage 请求返回 401 | 直接返回 `state: invalid`，刷新端点调用次数为 0 |
| Google / Gemini | 过期 access token，已有 refresh token | 原 provider 内部刷新未持久化统一轮换流程，失败时继续使用旧凭证 |

原 Codex 复现日志：`/tmp/cursor-byok-issue481-baseline.log`。其中明确记录 `Expected one token refresh, got 0; state=invalid`。

## 代码审查补充

OpenAI refresh 请求采用与现有设备授权交换一致的 form-urlencoded 格式。刷新请求最多发出一次；网络或服务端临时错误进入冷却，避免在响应可能已轮换 token 时立即重放旧 refresh token。Google 同样持久化短冷却和终止授权错误，并覆盖异常成功响应中只返回 refresh token 的情况。Google provider 的 401 测试确认错误交给宿主处理，且发生在任何模型输出之前。

本轮补充了四个边界：Google 冷却截止时间和 invalid 状态保持不变；不透明 Google access token 在缺少 `expires_in` 时获得保守过期时间；宿主对账号准备、provider 结果补丁和资源 action 使用同一把账号锁，并在 I/O 写入失败时保留待处理轮换；手动 quota refresh 只查询配额，不再次交换 refresh token。认证与手动刷新回归共 12 项通过；Windows 专用磁盘只读测试由 Windows CI 运行，不计入本机数量。

## 并发与冷却二次复核

自动审查通过后新增的行为检查仍发现两个缺口，已先复现失败再修复：

- 存在未保存的旧授权轮换时，用户完成新登录后两次 prepare 会把新登录凭据覆盖为旧值。现在每个运行时更新先按原快照保存待处理结果；新授权取代原快照时，旧待处理结果失效，不会变更其快照后重放。
- Google 刷新网络异常后，正常请求和延迟到达的 401 都可能再次交换 token；原回归计数为 3、预期为 1。网络异常现在也持久化期限，401 不能绕过未到期冷却或终止授权错误。
- 增加迟到 provider 配额补丁测试：模拟模型请求期间存在尚未落盘的轮换，先保存轮换，再拒绝基于旧快照的配额补丁；新凭据保持不变。

上述测试使用合成凭据、临时插件 worker 与临时状态文件，不触碰正式账号。待处理结果仍在进程内保存，没有新增跨进程崩溃恢复承诺。
